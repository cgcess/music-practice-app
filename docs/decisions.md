# Decisions (kickoff interview, 2026-10-22)
1. Installable PWA, vanilla TS + Vite, GitHub Pages; IndexedDB; Vitest. No framework.
2. Single validated store; versioned schema + migrations; UUIDs; JSON export/import backup.
3. No logs/history: SR state lives on the Song; Task keeps lastCompletedOn; dev-only console log.
4. Config in src/config.ts; user-facing values overridable via Settings record.
5. Invariants: Task minutes int 1-240; days "daily" or non-empty unique 0-6; Song title non-empty,
   intervalDays >= 1, ease within bounds, dueDate >= lastReviewed. (SR determinism/monotonicity
   tests come with the SR task.)
6. Gates: push/publish blocked; fixtures + migrations frozen behind .claude/unlock-data.
7. auto_commit: true. Evaluation and experiment loop skipped (not applicable).

## 2026-10-22 t001-conventions: conventions baseline
Store/schema/backup in src/data is the only IndexedDB path; fixtures + migrations frozen behind
.claude/unlock-data. Known limit: the bash freeze hook (R3) can be bypassed by quoted paths; Write/Edit deny is the real guard.

## 2026-10-22 t002-ui-shell: hash routing + h() for UI
UI lives in `src/ui/`; views are built with `h()` (text via text nodes, never `innerHTML`) and routed by `#/path` with `:param` segments.
`src/ui/` never imports `src/data/` directly. DOM tests use happy-dom via a per-file pragma; focus moves to `<main>` on navigation, not on initial load.

## 2026-10-22 t003-pwa: installable, offline, self-updating
vite-plugin-pwa 2.0.0 (generateSW, autoUpdate, `injectRegister: false`) builds the SW and manifest at build time; no runtime framework. Registration is hand-written in `src/pwa.ts` with `updateViaCache: "none"` (GitHub Pages serves `max-age=600`) and scope = app path; reload on `controllerchange` only when a previous controller existed. Shared origin: `cacheId: "music-practice"`; workbox cleanup deletes only `-precache-` caches containing this SW's scope, so other apps' caches are untouched. Theme colors, cache id and manifest values are build constants in `pwa-manifest.ts`/`vite.config.ts`, not tunable defaults, so outside `src/config.ts`. `navigator.storage.persist()` is requested at each startup. Deploy workflow uses Node 22 (plugin needs >=20.19).
Follow-up (t004): precache duplicates removed via `globIgnores` (icons and manifest come from the plugin's own entries); theme color is injected into `index.html` from `THEME_COLOR` via a `transformIndexHtml` plugin (single literal); `workbox-precaching` is pinned as a devDependency because a test imports its internals - bump together with vite-plugin-pwa.

## 2026-10-22 t005-today-timer: Today checklist + swipe timer
Data seam: `src/ui/ports.ts` defines `TodayPort` with UI-local types; `src/app/todayPort.ts` adapts the validated `Store` (all writes via `putTask`) and is wired in `main.ts`. `src/ui/` and `src/today/` never import `src/data/`. Prefs map Settings `timerSound/Vibrate/Overtime` to `{sound, vibrate, overtime}` via `getEffectiveConfig` (null settings fall back to `config.timer`).
`View` now returns `{el, dispose?}`; `mountShell(root, deps?)` calls the previous `dispose` before replacing `<main>` (and on unsubscribe), so Today's interval and wake lock cannot leak across routes.
The running timer is in memory only (start timestamp + injectable clock, `src/today/timer.ts`); nothing is persisted, no localStorage. Chime fires once per start and only if the tick is within `config.today.chimeGraceMs` of the target, so returning from the background never plays a missed chime. Undo (`src/today/undo.ts`) holds the previous `lastCompletedOn` in memory for `config.today.undoMs`. Tunables live in `config.today`. Audio: `audioSession.type="playback"`, AudioContext rebuilt on visible (no `resume()`). No schema change.

## 2026-10-22 t006-ios-look: iOS look and feel
Styling is token-based: `src/ui/base.css` defines light/dark CSS custom properties, safe areas, tab bar height and reduced-motion rules; views style only through tokens. Icons are SVG built in `src/ui/icons.ts` (SVG namespace, not `h()`).
Task colour is derived deterministically by `taskColor()` from a fixed palette, so it is not persisted and needs no schema change. Swipe now reports move/end; commit vibrates (feature-guarded, no-op on iOS) and `pointercancel` springs the row back. Add-task lives in a modal sheet (`src/ui/sheet.ts`, focus trap). Motion tunables live in `config.today`.

## 2026-10-23 t009-edit-tasks: edit and delete tasks on Today
Each row has a trailing pencil `button.edit` (44px, aria-label "Edit <name>", also on done rows) that opens the add-task sheet as "Edit task", pre-filled, with Save and Delete (sheet is one form, `openForm(task?)`; every open resets all fields). It stops `pointerdown` propagation so the row swipe (finish) never starts on it; `swipe.ts` is unchanged. Port gains `updateTask` (name/minutes/days only; id, lastCompletedOn, createdAt preserved), `deleteTask` (returns the full record) and `restoreTask`; `TaskSnapshot` is declared structurally in `ports.ts`. No schema change.
Delete is recoverable by an Undo toast ("Deleted X · Undo", `config.today.undoMs`) that restores the exact record; there is one toast, so it replaces a pending "Done" toast and completion undo is dropped. Songs and history hold no task reference, so delete has no dependents. Rejected: soft-delete flag (schema change), `confirm()`, long-press or header edit mode.
Running task: delete stops the timer and releases the wake lock (Undo restores the task, not the running state). A minutes edit applies from the next start (`targetMs` is fixed at start; the running row hides `.mins`); a name edit shows at once.

## 2026-10-23 t010-edit-mode: single Edit button on Today
Reverses t009's "Rejected: header edit mode" and removes the per-row pencil `button.edit`. A header `button.edit-toggle` flips an in-memory `editMode` (not persisted, no Settings/schema change); its text is the state ("Edit"/"Done") and its accessible name, with no `aria-pressed`. In edit mode each row shows a chevron, has no `button.act`, swipe or swipe background, and the row body (`role=button`, tabindex 0, "Edit <name>") opens the t009 edit sheet on click, Enter or Space. Edit mode stays on after Save, Delete, Undo and Add. No multi-select (user choice).
Running timer when entering edit mode: it keeps running (tick, wake lock, chime unchanged) and its time stays visible; it can be finished after tapping Done. Rejected: auto-pause/stop (new state, loses time) and auto-finish (marks work done unintentionally). A failed delete leaves the timer running.
Delete is guarded against double-tap by an in-flight flag plus `disabled`, both reset on failure and on opening the sheet. Folded in t009 review items 1-3 (undo expiry asserted via `after(config.today.undoMs)`, port rejects minutes 0, delete guard).

## 2026-10-23 t011-metronome: collapsible metronome on Today
A panel in `header.large-header` after the summary (`src/ui/metronome.ts`): collapsed it shows a toggle, the BPM and play/stop; expanded it adds -/+ and a range slider (`aria-label` "Tempo", `aria-valuetext` "N BPM"). Open state is in memory, default collapsed, not persisted. The task list is never hidden. Independent of the task timer and edit mode (separate env, own interval).
Tempo is one new Settings field `metronomeBpm` (integer within `config.metronome.minBpm..maxBpm`): `schemaVersion` 1 -> 2, migration `v1-to-v2` adds the literal 100 (not read from config, so the frozen migration cannot drift), fixture `tests/fixtures/v2-metronome.json`; `v1-basic.json` is untouched and `fixtures.test.ts` special-cases v1 (expects `metronomeBpm: 100`). Defaults, lookahead (100 ms), scheduler tick (25 ms) and click voice live in `config.metronome`; `getEffectiveConfig` overlays `metronome.bpm`. Port gains `getTempo`/`setTempo`; saved on slider `change` and on -/+ presses, not on `input`.
Timing: `metronomeScheduler.ts` queues clicks on the Web Audio clock while `next < audioNow + lookahead`, reading bpm per beat, so tempo changes apply from the next beat; no per-beat `setTimeout`. Audio: the metronome owns its own AudioContext, created and resumed inside the Play tap, closed on Stop; it does not share Feedback's context (that one is rebuilt on visible and has no `resume`). `audioSession.type = "playback"` when available. Background: when the page becomes hidden the metronome stops and closes its context; the user presses Play again (fresh gesture). No lock-screen audio or Media Session. Added a `stop` icon.
Rejected: localStorage / separate store for the tempo (unvalidated, breaks the store rule), sharing the chime context. Manual iPhone PWA check (silent switch, chime coexistence, backgrounding) pending.

## 2026-10-23 t013-repertoire: spaced-repetition scheduler and Repertoire tab
Part 1 of 2 (t014 puts the day's songs on Today with rating). The user learns songs outside the app and adds them; the app only keeps known songs from going stale. SR state stays on the Song; no history, no schema change (`suggestionPeriod` stays in the schema, unread and not shown).
Scheduler (`src/sr/`, pure; `today` is always a parameter): ratings rough/ok/solid. gap = max(intervalDays, days since lastReviewed, or since createdAt when never rated). rough: ease -0.20, interval = intervalDays/2 (scheduled, not gap); ok: gap x ease; solid: ease +0.15, gap x ease x 1.3. The interval uses the ease before the rating. Round, fuzz +-10% only when the rounded interval is >= 3 days (FNV-1a seed of id + today), clamp 1..365; ease rounded to 2 decimals and clamped 1.3..3.0. New song: ease 2.5, interval 1, due today + seeded 0..7 days (id + add date) so a bulk add spreads over a week. Pick order: dueDate <= today, oldest first, ties by hash of the id only (stable across days). Daily selection: songs rated today plus the first songsPerDay - rated of the pick order; no refill after rating; an unrated shown song stays shown. All tunables live in `config.sr`; `maxSongsPerDay` (10) in `config`.
Repertoire tab: list (title, due in words, overdue reads "today", no overdue count), add, bulk add (trim, drop blanks, skip case-insensitive duplicates of existing and earlier lines, report added/skipped), edit sheet with rename and delete + Undo restoring the exact record, `songsPerDay` stepper (0..max, saved to Settings, rounded and clamped in the port). Port seam as t005 (`RepertoirePort`, `src/app/repertoirePort.ts`); the toast is a small local copy, not a shared extraction.
Rejected: a learning/known state; four ratings; a weekly budget or plan for `suggestionPeriod`; resetting rough to 1 day or a fixed short return; a "last played" field when adding; noise only in the pick order (songs added together would keep coming due in clumps); unseeded randomness (breaks determinism tests); a date-seeded tiebreak (a shown song could drop off); refill after rating; an overdue count; per-song "play tomorrow"/"reset"; building the Settings tab now.

## 2026-10-23 t014-today-songs: Songs section on Today with swipe-to-rate
Part 2 of 2. `section.songs` after the task groups: t013's daily selection, no timer or minutes. `songsPerDay = 0` hides it; an empty selection reads "Nothing to play today"; all rated reads "All done for today". Port gains `listTodaySongs`, `rateTodaySong` (returns the previous record, rejects when already rated today, so no re-rating except Undo) and `restoreTodaySong`; `src/ui` still never imports `src/data`. No schema change, no persisted selection or rating.
Rating: swipe left (new sibling `swipeReveal.ts`; `swipe.ts` and task rows untouched), or tap/Enter/Space on the row, reveals rough/ok/solid (aria-label "Rate <title> <rating>", 44px). One open row at a time (opening another, swipe right, or a tap elsewhere closes it). Rating applies t013's scheduler, greys the row, and shows the single Undo toast ("Rated <title> <rating> · Undo"), which replaces a pending task toast. Edit mode: no swipe, no open, no buttons.
Label: kept in memory only; after a reload a rated row reads "Rated" (user decision).
Cap (user decision): songs rated today always stay visible even if `songsPerDay` drops below their count; unrated songs fill `max(0, songsPerDay - rated)`. `dailySelection` changed accordingly.
Top-up: when rated + due < `songsPerDay`, `planTopUp` pulls the soonest-due future songs and `listTodaySongs` writes `dueDate = today` through the validated store, so the selection is stable across reloads and the Repertoire tab reads "today" with no `dueText` change. Accepted side effect: pulled songs' dueDate moves to today permanently. A failed write falls back to the unmodified selection. Songs created today (local date of `createdAt`, not a string slice) are not pulled unless nothing is rated or due.
Open-row close: a pointerdown on another unrated song row does not close the open row from the document handler (re-rendering mid-gesture would detach the touched row); that row's own open/toggle closes it. Any other pointerdown, including on a rated row, closes it.

Add-time rule (first-day rule, user decision 2026-10-23): if every existing song was created today (local date), a new song is due today while fewer than `songsPerDay` songs are already due today; otherwise it uses `newSong(..., {minOffset: 1})`, due tomorrow or later, so it cannot displace a shown song. Single and bulk adds behave the same. On that first day only, a song may be added after Today already showed one; from the next day the selection is fixed once non-empty.
Rejected: a view-side due override (Repertoire cannot see the selection), persisted ids (schema bump), always-visible buttons, a rating sheet.
Manual check pending on a real iPhone: touch swipe feel (pointer capture, click swallowed after a drag) and VoiceOver on the row and rating buttons.

## 2026-10-23 t017-ui-alive: progress gradient header and reward touches on Today
